# 기술 의사결정 (Trade-offs)

A vs B / 장단점 / 선택 이유

---

## 인프라

### CI/CD: Jenkins vs GitHub Actions → GitHub Actions
- Jenkins: 커스터마이징 자유로움 / 별도 서버 필요, 메모리 많이 써서 작은 인스턴스에서 앱이랑 같이 돌리기 부담
- GitHub Actions: 서버 필요 없음, YAML 하나로 구성, GitHub 연동 / 복잡한 파이프라인엔 제약
- 선택 이유: 1인 프로젝트라 CI 서버 운영 비용이 더 큼

### DB: EC2 내 MySQL 컨테이너 vs RDS → RDS (로컬은 컨테이너)
- 컨테이너: 무료, 단순 / EC2 장애 시 데이터 위험, 백업 직접 관리
- RDS: 백업·장애 대응 관리형 / 비용
- 선택 이유: 실제 런칭할 서비스라 데이터 안전성 우선. compose는 앱 + nginx만

### 실거래가 배치: Spring Batch vs @Scheduled → @Scheduled
- Spring Batch: 재시작, 청크 처리, 이력 관리 / 메타 테이블, Job·Step 설정 부담
- @Scheduled: 설정 거의 없음 / 실패 재처리 직접 구현
- 선택 이유: 하루 1번 API 호출해서 저장하는 규모. IPO 프로젝트에서 Spring Batch 써봤는데 이 정도면 오버킬

### 테스트 DB: H2 vs Testcontainers → H2 (MySQL 모드)
- H2: 의존성 하나, CI에서 Docker 불필요 / MySQL이랑 동작 차이 가능
- Testcontainers: 운영이랑 같은 MySQL / Docker 필요
- 선택 이유: 지금은 컨텍스트 로딩 테스트 수준. 네이티브 쿼리 생기면 다시 검토

### 운영 ddl-auto: update vs validate (미정)
- 런칭 전까지 update, 런칭 직전에 결정

### 규칙 강제: 문서만 vs 코드(린터·테스트·훅) → 코드
- 문서만: 작성 쉬움 / 사람·에이전트 모두 놓침
- 코드: 위반 시 커밋 자체가 막힘 / 설정 유지 비용, 문서와 동기화 필요
- 선택 이유: 문서에만 있는 규칙은 잘 안 지켜짐. CLAUDE.md 규칙을 ArchUnit, ESLint로 옮기고 훅으로 커밋 전 검사

### Git 훅 관리: pre-commit(Python) vs husky vs core.hooksPath → core.hooksPath
- pre-commit: 다양한 훅 생태계 / Python 설치 필요
- husky: 프론트에서 많이 씀 / 루트 package.json 필요, Node 의존
- core.hooksPath: 추가 도구 없음, 셸 스크립트만 / 클론 후 설정 1회 필요
- 선택 이유: Java + Node 모노레포라 특정 언어 도구에 묶이지 않는 게 나음. 훅은 --no-verify로 우회 가능해서 CI에서 같은 검사 한 번 더

### 백엔드 아키텍처 검사: 리뷰만 vs ArchUnit → ArchUnit
- 리뷰만: 추가 의존성 없음 / 놓치기 쉬움
- ArchUnit: 계층 규칙을 테스트로 강제 / 테스트 의존성 1개
- 선택 이유: 계층·엔티티 규칙은 패턴이 명확해서 테스트로 잡기 좋음

## 데이터 모델

### 보유 현황 저장 vs 거래 이력 합산 → 둘 다 저장
- 이력만: 데이터 하나로 관리 / 평가액 계산할 때마다 전체 합산, 평균 매입가 계산 복잡
- 둘 다: 조회 빠름 / 두 테이블 정합성 관리 필요 (트랜잭션으로 처리)
- 선택 이유: 평가액을 WebSocket으로 계속 다시 계산해야 해서 현재 상태를 바로 읽어야 함

### 매수/매도 테이블 분리 vs 통합 → 통합 (trade_type)
- 컬럼 같음, 거래 내역 시간순 조회 편함

### 회원/자금 1:1 분리 vs 통합 → 통합
- 분리할 근거(변경 빈도, 락 범위, 다계좌)가 MVP에선 약함

### 아파트 구매 단위: 대표가 1개(중앙값) vs 최근 거래 목록 → 최근 거래 목록
- 대표가: 구현 단순, 이상치에 강함 / 고르는 재미 없음
- 거래 목록: 층·가격 골라서 사는 재미 / 목록 화면 추가
- 선택 이유: 캡처해서 공유하는 게 핵심이라 "몇 층 샀다"가 있는 게 나음. 최근 6개월로 제한해서 과거 거래가로 차익 보는 문제 차단

### 시세 기준
- 국토부 데이터는 계약 완료 기록이라 매물(호가) 없음 → 최근 6개월 실거래가를 시세로 봄
- 6개월 내 거래 없는 단지는 추천 제외

### 같은 집 독점 vs 공유 구매 → 공유
- 독점: 현실적 / 동시성 제어 필요, 인기 매물 품절
- 공유: 같은 조건 한 채를 누구나 구매 가능
- 선택 이유: 게임 재미, 일정

### 배치: 전체 삭제 후 재적재 vs 증분(upsert) → 증분
- HOUSE가 APT_DEAL PK를 참조해서 재적재하면 PK 바뀌고 참조 깨짐

### 거래 UK: (단지 id, 전용면적, 층, 거래금액, 계약일)
- 국토부 데이터에 거래 고유번호 없음. 해제여부는 나중에 바뀌어서 제외
- 한계: 동(棟) 정보가 없어서 동만 다른 같은 조건 거래는 하나 누락 (드묾)

### 금액 타입: long vs BigDecimal → 원 단위 long, 평균 매입가만 BigDecimal

## 범위

### 기능 추가 vs 프론트 직접 구현 → 프론트 직접 구현
- 풀스택 지원이라 기능 하나 더보다 프론트 직접 짠 게 중요
- 자연어 검색은 10/17까지 MVP 끝나면 추가

### 자연어 검색: SQL 직접 생성 vs 필터 JSON → 필터 JSON
- 사용자 입력 예측 불가 → LLM은 필터만 추출, 쿼리는 코드에서 생성
