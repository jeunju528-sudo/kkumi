# 036. 테스트 범위: 돈 계산과 도메인 규칙만 자동 테스트, 나머지는 수동 확인

## 상태
확정 (2026-10-13)

## 배경
기존 규칙은 "Service에 새 메서드를 추가하면 성공 1개 + 실패 1개 테스트 필수"였다. 런칭(10/24)과 MVP 게이트(10/19)까지 남은 기간에 매수·매도, 가상 시세, 평가액·WebSocket, 실거래가 배치, 추천, 집 사기, 프론트 연결이 남아 있어, 단순 조회 메서드나 Controller까지 테스트를 쓰면 기능 개발 시간이 부족했다. 시드 선택 API의 Controller 테스트(MockMvc)를 쓸지 정하는 과정에서 범위를 다시 정했다.

## 결정
- 자동 테스트 필수 (구현 전에 테스트 먼저)
  - 심장 ①: 매수·매도 잔액·보유량 계산
  - 심장 ②: 포트폴리오 평가액 계산
  - 심장 ③: 실거래가 배치 수집 (증분 upsert)
  - 도메인 규칙: 변신 단계 경계(0 / 1 / 2~4 / 5 이상, 음수), 추천 조건(평가액 ≥ 집값×40%), 집 결제(현금에서 40% 차감, 부족하면 실패)
- 자동 테스트 생략, 화면 연결 때 수동 확인
  - 단순 조회·저장 Service, Controller(MockMvc), DTO 변환, 설정
- 이미 작성한 테스트는 지우지 않고 유지한다
- 판단 기준: 틀려도 화면에서 바로 보이면 수동 확인, 틀린 것이 숫자 속에 숨으면 자동 테스트

## 이유
- 이 게임에서 사용자가 눈치채기 어려운 오류는 돈 계산과 등급 경계다. 잘못돼도 화면이 정상으로 보여서 수동 확인으로는 놓친다
- 상태 코드·쿠키·화면 이동 같은 API 동작은 프론트를 연결하면 바로 드러나고, 브라우저 개발자 도구로 확인할 수 있다
- 제한된 기간에 테스트 시간을 위험이 큰 곳에 모으는 편이 전체 품질에 유리하다

## 포기한 대안
- Service 메서드마다 성공·실패 테스트(기존 규칙): 빠짐없이 검증되지만 단순 메서드까지 시간이 들어 일정 안에 기능을 못 끝냄. 포기
- Controller 테스트(MockMvc)까지 작성: 409·쿠키를 자동으로 지킬 수 있지만 `@WebMvcTest`, Security 설정 대응 등 준비 비용이 큼. 포기 (런칭 후 재검토)
- 테스트 없이 전부 수동 확인: 가장 빠르지만 돈 계산 오류를 놓칠 위험이 큼. 포기

## 결과
- API 응답(상태 코드, 에러 바디, 쿠키)은 회귀 테스트가 없어서, 나중에 바뀌어도 자동으로 잡히지 않는다. 화면 연결과 통합 테스트 기간(10/21~23)에 수동으로 확인한다
- 런칭 후 여유가 생기면 Controller 테스트를 추가할지 다시 정한다
- ArchUnit·ESLint 규칙 검사는 그대로 유지한다
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 생략 대상(단순 Service, Controller)의 테스트 작성을 먼저 제안하지 않고, 필수 대상의 테스트는 생략을 제안하지 않는다. 관련: 006, 035.
