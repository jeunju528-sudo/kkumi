# 062. 하락 알림 판정: 시세마다 DB 조회 대신 메모리 장부

## 상태
확정 (2026-11-18)

## 배경
- 059에서 시세 tick → Kafka → 컨슈머 그룹 `price-alert`가 보유자 판정(현재가 ≤ 평균 매입가 × 97%)으로 결정
- 첫 설계는 메시지 1건마다 "그 종목 보유자 + 오늘 받은 회원"을 DB에서 조회해 판정. 지금(종목 20개)은 5초에 20번이지만, 종목이 100배면 5초마다 DB 왕복 2,000번
- 파티션·컨슈머를 늘려도 DB 왕복 수는 그대로라 DB가 병목

## 결정
- 판정은 서버 메모리 장부 `PriceAlertBook`으로 한다. 시세 판정 중 DB 조회 없음
  - ① 알림 장부: 종목 → 기준가(평균 매입가 × 97%, 원 단위 내림) 정렬 → 회원. `TreeMap.tailMap(현재가)`로 기준가 ≥ 현재가 구간만 꺼냄
  - ② 받은 목록: (회원, 종목, 날짜). 날짜가 키에 있어서 자정 작업 없이 다음 날 자동으로 "안 받음". 날짜가 바뀐 뒤 첫 판정 때 지난 날짜 줄 정리
- DB는 두 경우만: 서버 시작 때 장부 로드(`PriceAlertBookLoader`, 보유 전체 + 오늘 알림), 알림이 생길 때 종목 조회 1번 + `notification` 저장
- 장부 갱신: 매수·전량 매도 커밋 후 서버 안 이벤트(`HoldingChangedEvent` → `@TransactionalEventListener(AFTER_COMMIT)`)
- 컨슈머 3개(`spring.kafka.listener.concurrency: 3`). 파티션 3개를 하나씩 맡음
- `notification` 유니크 키 (회원, 종목, 날짜)는 마지막 방어선으로 유지

## 이유
- 시세는 5초마다 전 종목이 오고, 알림은 드물게 생김 → 자주 하는 일(판정)은 메모리, 드문 일(저장)만 DB
- 메모리 크기는 "회원 × 종목"이 아니라 보유 건수에 비례. 5만 명 × 평균 10종목 = 50만 줄 × 약 200바이트 ≈ 100MB (t3.medium 4GB에 충분)
- 기준가를 원 단위 내림 `long`으로 저장: 현재가가 정수라 `현재가 ≤ 내림(평단 × 97%)`와 `현재가 ≤ 평단 × 97%`의 결과가 같음. 비교가 단순하고 메모리도 작음
- 키 = 종목코드라 같은 종목은 늘 같은 파티션 → 같은 컨슈머 스레드. 같은 종목 판정이 동시에 돌지 않아 받은 목록 확인·추가가 겹치지 않음
- AFTER_COMMIT: 롤백된 거래(현금 부족 등)가 장부에 들어가지 않음
- 서버 안 이벤트: `TradeService`가 notification 패키지를 몰라도 됨

## 포기한 대안
- 메시지마다 DB 조회 후 자바에서 거르기: 단순 / 보유자 전체를 매번 가져옴, 규모 커지면 병목
- DB 안에서 거르는 쿼리(where 판정 + not exists): 결과는 대부분 0건 / 쿼리 수는 메시지 수 그대로
- batch listener로 묶어 `IN` 조회: 쿼리 수 감소 / 종목별 가격이 달라 쿼리가 복잡, 여전히 DB 왕복
- Kafka Streams state store(로컬 RocksDB + changelog 토픽 복구): 대규모 정석 / 사실상 새 기술, 11/20 마감 안에 무리
- 받은 여부를 ① 장부의 칸으로: 표 하나 / 알림 보낼 때마다 정렬 장부를 고쳐야 하고 시세 판정·거래가 같은 표를 동시에 고침
- 자정 스케줄러로 받은 목록 비우기: 직관적 / 스케줄러가 안 돌거나 자정에 서버가 꺼져 있으면 틀림

## 결과
- 서버 재시작 때 보유 전체를 한 번 읽음 (보유 건수에 비례해 기동 시간 증가)
- 장부가 서버 메모리에 있어서 서버가 2대 이상이면 거래 이벤트가 다른 서버 장부에 안 감
  - 확장 조건: 서버를 늘리면 거래 이벤트를 Kafka(키 = 종목코드)로 발행해 같은 파티션 컨슈머가 장부 갱신. 서버마다 자기 파티션 종목 장부만 들고, 리밸런스 때 새로 맡은 종목만 DB에서 다시 채움. 그 이상은 Kafka Streams 검토
- 알림 저장 후 커밋 전에 DB가 실패하면 받은 목록에는 표시돼 그날 그 종목 알림이 빠질 수 있음 (드문 경우, 감수)
- 059 "포기한 대안"의 메모리 상태는 판정용 장부에 한해 이 ADR로 채택. 알림함 데이터는 059대로 DB
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 시세 판정에 DB 조회를 다시 넣거나 장부를 Redis 등 외부 저장소로 옮기는 제안을 하지 않는다. 관련: 045, 059.
