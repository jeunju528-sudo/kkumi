# 031. 인증 방식: 세션 대신 JWT, HttpOnly 쿠키로 전달

## 상태
확정 (2026-10-07)

## 배경
카카오 로그인(030) 성공 후 로그인 상태를 유지할 방법이 필요하다. 서버가 상태를 저장하는 세션과 서명된 토큰(JWT) 중 하나를 정하고, 토큰을 브라우저에 전달·보관하는 방법(쿠키 또는 Authorization 헤더)도 정해야 했다. 또 카카오 로그인 직후 시드머니를 고르기 전에는 회원(`Member`)이 없어서(`Member.join`이 `seedMoney`를 필수로 받음), 이 가입 미완료 상태를 어떻게 이어갈지도 정해야 했다.

## 결정
- 로그인 상태는 JWT로 유지한다. 세션은 사용하지 않는다
- JWT는 HttpOnly 쿠키로 전달한다. 서버가 응답의 `Set-Cookie`로 심고, 브라우저가 요청마다 자동으로 보낸다. `SameSite=Lax`를 쓰고, `Secure`는 HTTPS 전환 후에 켠다
- 가입 미완료(카카오 로그인은 했지만 시드 선택 전)는 kakaoId와 닉네임을 담은 임시 JWT(짧은 만료)로 이어간다. `POST /api/members/seed`에서 회원을 만들고 memberId가 담긴 정식 JWT로 교체한다

## 이유
- 배포할 때마다 컨테이너가 새로 만들어져서 서버 메모리의 세션은 사라짐. JWT는 서버가 저장하지 않아 재배포 후에도 로그인이 유지됨
- 세션을 유지하려면 별도 저장소(Spring Session JDBC 등)가 필요한데, 새 의존성과 테이블이 생겨 새 기술 상한선(024)에 걸림
- HttpOnly 쿠키는 자바스크립트가 읽을 수 없어 XSS로 토큰을 훔치기 어렵고, 카카오 로그인의 리다이렉트 흐름과 WebSocket(STOMP) 연결에서 자동으로 전달됨
- 가입 미완료 상태를 DB 없이 임시 토큰에 담아 이어갈 수 있음

## 포기한 대안
- 인메모리 세션: 구현이 가장 단순함 / 배포마다 전원 로그아웃. 포기
- 세션 + 저장소(Spring Session JDBC 등): 재배포에도 유지되고 서버가 세션을 강제로 끊을 수 있음 / 새 의존성·테이블 추가(024 협의 필요). 포기
- JWT를 Authorization 헤더로 전달(프론트가 저장): CSRF에서 자유로움 / 저장소의 토큰을 자바스크립트가 읽을 수 있어 XSS에 취약, 리다이렉트로 토큰을 넘기려면 주소에 실어야 함, 요청·STOMP 연결마다 토큰을 붙이는 코드가 프론트에 필요. 포기

## 결과
- 발급한 JWT는 서버가 강제로 무효화하기 어려움. 탈취되면 만료 전까지 유효하므로 만료를 짧게 둠 (만료 시간은 구현 PR에서 정함) (감수). 로그아웃은 쿠키 삭제로 처리
- 쿠키 방식이라 CSRF 가능성이 있음 → `SameSite=Lax`로 완화. 쿠키로 인증하는 쓰기 API가 늘어나면 CSRF 토큰 도입을 다시 검토
- 서명 키는 비밀값이라 환경변수(`.env`, EC2 `.env`, compose 전달)로만 관리하고 커밋하지 않음
- `Secure` 쿠키는 http(IP) 접속에서 브라우저가 보내지 않으므로, 도메인·HTTPS 전환(10/21) 전까지는 끄고 이후에 켬
- 리프레시 토큰은 이 결정의 범위 밖. 필요해지면 새 ADR로 정함
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 세션 도입과 토큰을 프론트 저장소에 보관하는 방식을 먼저 제안하지 않는다. 관련: 024, 030.
