# 019. 금액 타입: 원 단위 long, 평균 매입가만 BigDecimal

## 상태
확정 (2026-10-03)

## 배경
금액을 어떤 타입으로 다룰지 정해야 했음.

## 결정
금액은 원 단위 `long`으로 다룬다. 평균 매입가만 `BigDecimal`을 쓴다.

## 이유
- 평균 매입가는 나눗셈 결과라 소수점이 생긴다. 정수 `long`으로 두면 소수점이 버려져 오차가 쌓이므로 `BigDecimal`을 쓴다
- 그 외 금액(현금, 주가, 집값, 손익)은 원 단위 정수라 `long`으로 충분하다

## 포기한 대안
- 금액 전부 `BigDecimal` (이 프로젝트에서 비교한 기록은 없음)
- `double` / `float` (이진 부동소수점 오차 때문에 금액에 쓰지 않는다)

## 구현 시 정한 것 (2026-10-15)
- 평균 매입가: scale 4, `RoundingMode.HALF_UP` (DB 컬럼 `precision 19, scale 4`와 동일)
  - 가중평균 나눗셈 1회에만 반올림
- 실현손익: (체결가 − 평균 매입가) × 수량을 `BigDecimal`로 계산한 뒤 마지막에 원 단위(scale 0) `HALF_UP`으로 1회 반올림 → `long`
  - 중간 반올림 없음 (오차 누적 방지)
  - `HALF_UP`은 0에서 먼 쪽으로 반올림 → 손실도 대칭 (−1234.5 → −1235)
- 포기한 대안: `HALF_EVEN`(은행가 반올림). 반올림 오차가 한쪽으로 쌓이지 않음 / 거래 1건 단위라 누적 이점이 작고, 결과를 설명하기 어려움

## 결과
`double` / `float`는 CLAUDE.md에서 금지이며 엔티티·DTO는 `ArchitectureTest`가 검사한다.
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 금액에 `double` / `float`를 쓰지 않는다.
