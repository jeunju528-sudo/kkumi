# 064. AI 관제센터: 장애·보안 이벤트를 AI가 1차 분석해 Slack으로, Elasticsearch는 관제 로그 저장으로, AI 자산 코치는 보류

## 상태
확정 (2026-11-26)

## 배경
- 운영 중 장애·보안 이벤트는 개발자가 로그를 직접 열어 확인하는 구조라 1차 분석 자동화가 필요함
- 061의 Elasticsearch 단지명 자동완성은 MySQL LIKE로도 되는 기능이라 도입 근거가 약함. Elasticsearch는 원래 로그 수집·검색(ELK)에서 많이 쓰임
- EC2는 프리 플랜이라 t3.small(2GB)까지만 쓸 수 있고 Kafka가 이미 올라가 있음(059). 크레딧 약 $69, 2027-01-10 만료
- 051 AI 자산 코치에서 하려던 tool calling·호출 루프 제어·숫자 검증·감사 로그·Redis는 관제의 조사 단계에도 그대로 필요함
- 2025~2026 국내 금융권·플랫폼 침해사고는 IPS·IDS·웹방화벽이 있는 환경에서 발생. 원인은 요청 모양이 아니라 의미를 봐야 잡히는 것들
  - 2026 금융권 연쇄 침해: 핵심 거래 시스템 밖의 업무지원·대출모집 시스템, 인증 우회와 권한을 넘는 조회, 여러 나라 IP로 바꿔 가며 반복 요청
  - 롯데카드(2025): 자산 목록에서 빠진 웹로직 서버 1대의 패치 누락, 조금씩 가져가는 저속 유출로 이상 탐지 우회
  - SGI서울보증(2025): VPN 기본 비밀번호 미변경, 전산망에 연결된 백업
  - 쿠팡(2025): 퇴사자 인증 서명키 미갱신, 개인정보 페이지 대량 조회 임계치 미흡, 접속 기록 삭제

## 결정
- 진행 순서: 관제 1단계 → 관제 2단계. AI 자산 코치(051)는 보류
  - 1단계: 앱·DB 에러 → LLM 요약 → Slack `#alert-error`. Spring 안에서만 처리, Elasticsearch 없이 꿈이 서버에 배포
  - 2단계: 앱 계층 보안 탐지 → `#alert-security`, 로그 저장 Elasticsearch·Kibana·Filebeat(관제 서버)
- 2단계 보안 탐지 범위 (웹방화벽이 못 보는 앱 계층 행위 중심)
  - 권한 초과 조회: 회원별 403·404 몰림 (남의 리소스 id 시도)
  - 반복·대량 조회: 회원별·API별 조회량 임계치, 넘으면 자동 1차 차단 + 알림
  - 같은 토큰이 짧은 시간에 여러 IP에서 사용
  - 저속 유출: 순간 임계치 대신 평소 대비 하루 누적 조회량
  - 정찰: 404 경로 스캔(`index.php`, `/.env`, `/.git` 등)은 IP별 하루 요약. 같은 IP가 실제 API에서 401·403을 내면 위험도 상승. `/.env`, `/.git`, `/actuator`가 200이면 즉시 높음
  - 외부 노출 자산 점검: 매일 열린 포트·경로를 허용 목록과 비교
  - 로그 분리 보관: 로그를 서비스 서버와 분리된 관제 서버로 바로 전송
- 흐름: 규칙이 1차 판정·자동 차단 → LLM이 조회 전용 tool로 조사 → 관련 이벤트 묶기, 위험도, 확인할 것 작성 → Slack. 차단 해제와 최종 판단은 사람
- 2단계 조사(AI 보안 분석가): 051의 tool calling 설계를 옮겨 옴
  - 조회 전용 tool 후보: IP별 최근 요청(Elasticsearch), 회원별 최근 403·404 수, 토큰이 쓰인 IP 목록, 외부 노출 점검 결과. 차단·해제 같은 실행 tool 없음
  - tool 자동 실행을 끄고 호출 루프 직접 제어 (화이트리스트, 이벤트당 최대 호출 횟수)
  - 숫자는 tool 결과로만 채움 (자리표시자 치환, 051)
  - 감사 로그: LLM이 부른 tool, 인자, 결과 요약, 최종 보고
  - 로그 경유 프롬프트 인젝션 방어: 로그 속 요청 경로·헤더는 공격자가 넣은 문자열이라 지시가 아닌 데이터로 구분해 전달, 길이 제한, tool 화이트리스트로 피해 범위 제한
- Redis(051에서 이동): 탐지 카운터(INCR + 만료로 시간 창 집계)와 자동 차단 목록
- LLM은 Spring AI ChatModel + Gemini(051에서 이동). 1단계에서 단순 호출로 먼저 연결, 2단계에서 tool calling 추가. 1단계 호출 한도는 같은 에러 묶어 보내기
- Elasticsearch 용도를 단지명 자동완성(061)에서 관제 로그 저장으로 변경
- 실행 위치: 개발은 로컬 Docker. AWS에는 연동 확인·시연 때만 별도 관제 서버(c7i-flex.large, 4GB)를 켜고 끝나면 중지. 꿈이 서버(t3.small)에는 2단계 구성요소를 올리지 않음

## 이유
- 1단계를 먼저: LLM 단순 호출(1단계) → tool calling(2단계) 순서로 새 개념이 단계적으로 늘어남
- AI 코치 보류: 관제 2단계 조사에서 tool calling·숫자 검증·감사 로그·Redis를 모두 다룸. 기능 하나를 깊게 만드는 편이 범위와 일정에 유리
- 웹방화벽은 요청 모양, 관제는 요청 의미: 최근 사고가 정상 요청처럼 보이는 권한 초과 조회·저속 유출이라 앱 계층 행위 탐지가 보완 역할. 인젝션·XSS 패턴 차단은 웹방화벽 영역이라 범위에서 뺌
- 규칙이 먼저 거르고 AI는 해석만: 공격 속도가 분 단위라 차단은 규칙이 자동으로, AI는 묶기·요약. 비용·오탐이 줄고 판정 근거가 코드로 남음
- 서비스와 관제 분리: 관제가 죽어도 서비스는 영향 없고, 서비스가 죽어도 관제가 알림. 서비스 서버가 침해돼도 로그가 남음
- LLM에 넘기기 전 민감정보 마스킹(토큰, 쿠키, 카카오 ID 등), 같은 이벤트는 묶어서 한 번만 보냄(Slack 전송 제한, 토큰 비용)

## 포기한 대안
- Elasticsearch 단지명 자동완성 유지(061): 형태소·부분 일치 설명 가능 / LIKE로도 되는 기능, 관제와 같이 하면 범위 초과
- 인젝션·XSS 패턴 탐지 중심: 설명이 쉬움 / 웹방화벽과 역할 중복, 최근 사고 유형과 거리
- 관제 로그를 CloudWatch로만: AWS 관리형이라 편함 / 직접 운영 경험이 적고 크레딧 사용. EC2 생존 확인 같은 서버 밖 감시만 2단계에서 검토
- 꿈이 서버에 같이 올리기: 서버 1대로 단순 / t3.small 2GB에 Elasticsearch까지 못 올림, 서비스와 관제가 같이 죽음, 로그 분리 보관 불가
- 꿈이 서버 사양 올리기: 프리 플랜에서 t3.medium 불가
- AI 코치 먼저: 051 설계 완료 / 관제 시연이 12월 말로 밀림
- AI 코치와 관제 둘 다: 사용자용 AI와 운영 AI 사례 둘 / 같은 기술을 두 번 구현, 범위 증가
- 관제는 요약만(tool 없음): 구현 단순 / tool calling 경험이 빠짐

## 결과
- 새 기술 (024 예외): Spring AI + Gemini, Redis(051에서 이동), Elasticsearch·Kibana·Filebeat(관제 로그 한정), Slack Incoming Webhook. CloudWatch는 2단계 검토
- 잃는 것: 사용자가 직접 쓰는 AI 기능, 회원별 userId 주입 사례(관제 사용자는 개발자뿐). AI 코치 재개 조건: 관제 2단계 완료 후 시간이 남을 때, 051 설계 그대로
- Webhook URL은 비밀값: `.env`, GitHub Secrets, 서버 `.env`로만. Elasticsearch·Kibana는 인증을 켠 상태로만 띄움
- 구현 단계에서 확정: Kafka를 관제 이벤트 통로로 쓸지(059 토픽과 분리), 탐지 규칙의 숫자, 메시지 묶는 시간 범위, 관제 서버 compose 구성과 힙 크기
- 보안 탐지 시연은 우리 서버만 대상으로, 직접 만든 스크립트로 진행
- 크레딧 만료(2027-01-10) 뒤 AWS 시연이 안 되면 로컬 시연 영상과 캡처로 대체
- 처음 나오는 개념(Spring AI 연결, Slack 전송, tool 호출 루프, Redis 카운터, Filebeat 수집, 탐지 규칙)은 개발자가 직접 작성 (045)
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 2단계 구성요소를 꿈이 서버(t3.small)에 올리거나, AI가 장애·보안 판정과 차단 해제를 확정하는 구조, 관제 tool에 실행 기능(차단·해제·삭제)을 넣는 구조를 제안하지 않는다. 관련: 024, 045, 051, 059, 061, 063.
