# 053. Kafka를 AI 코치보다 먼저 도입: 체결 이벤트 → 즉시 평가액 푸시

## 상태
확정 (2026-11-11)

## 배경
- 051은 런칭 후 AI 자산 코치(약 2주)를 먼저 하고, Kafka는 그 뒤 연습용으로 도입하기로 함
- 지원 예정 공고(2026-11-17 마감)의 기본 자격 요건에 Kafka가 있음. 051 순서대로면 마감 전까지 Kafka 사용 경험이 없음
- 지금 평가액 푸시는 5초 주기(046)라 매수·매도 직후 화면 반영이 최대 5초 늦음

## 결정
- 순서: 11/14 런칭 → 11/15~16 Kafka → 이후 AI 코치(051)
- 범위: 매수·매도 체결 이벤트 1종만. 거래 커밋 후 발행 → 컨슈머가 그 회원 평가액을 바로 계산해 개인 큐로 푸시(046 경로 재사용). 5초 주기 푸시는 그대로 둠
- 발행 시점: 트랜잭션 커밋 후 (`@TransactionalEventListener(AFTER_COMMIT)`). 롤백된 거래는 발행하지 않음
- 메시지 키: 회원 ID (같은 회원의 체결 순서 유지)
- 실서버: 브로커 1대(KRaft, ZooKeeper 없음)를 Compose 컨테이너로 추가. Kafka 도입일에 EC2 t3.small(2GB) → t3.medium(4GB)
- 심장 ① 저장 로직은 바꾸지 않음. `TradeService`에는 이벤트 발행 1줄만 추가 (개발자 작성)

## 이유
- 지원 자격 요건을 마감 전에 실서버 경험으로 채움
- 체결 이벤트는 기존 흐름(거래 → 평가액 → WebSocket)에 붙어 범위가 작고, 사용자 체감(즉시 반영)이 있음
- 커밋 후 발행: 커밋 전에 보내면 롤백된 거래로 평가액이 푸시될 수 있음
- 메모리: Kafka는 JVM 프로세스라 Spring 앱과 같이 2GB에 올리면 OOM 위험

## 포기한 대안
- 051 순서 유지(AI 코치 먼저): 설계가 이미 있음 / 마감 전 Kafka 경험 없음
- 로컬 Compose에서만 사용: 비용 없음 / "실서버 운영"을 말할 수 없음
- t3.small 유지 + Kafka 힙 최소화: 비용 없음 / 앱과 브로커가 메모리를 나눠 써서 OOM 위험
- 체결 외 이벤트까지(감사 로그, 집 사기): 소재가 늘어남 / 이틀 안에 끝내기 어려움

## 결과
- 비용: AWS 크레딧 $98.97, 2027-01-10 만료(2026-11-11 기준). 11월 1~11일 지출 $14.67(하루 약 $1.3, RDS가 가장 큼). t3.medium은 t3.small보다 하루 약 $0.62 더 듦(서울 온디맨드 $0.052 vs $0.026/시간). 만료 전에 크레딧을 넘을 가능성이 있어 AWS Budgets 알림 설정 필요. 만료 후 인프라 유지 여부는 12월에 결정
- 새 개념(프로듀서, 토픽, 파티션 키, 컨슈머 그룹, 오프셋, 커밋 후 발행)은 개발자가 직접 작성 (045)
- 컨슈머 실패 시 재시도·DLQ는 이번 범위 밖. 5초 주기 푸시가 남아 있어 푸시 1건이 빠져도 최대 5초 뒤 반영됨
- AI 코치 일정은 Kafka 이후로 밀림 (051 내용은 그대로)
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 Kafka 범위를 체결 이벤트 밖으로 넓히거나 런칭 전에 Kafka 작업을 제안하지 않는다. 관련: 024, 045, 046, 051.
