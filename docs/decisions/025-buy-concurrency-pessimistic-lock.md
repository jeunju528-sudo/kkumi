# 025. 매수 동시성: 낙관적 락·Redis 락 대신 비관적 락(Member 행)

## 상태
확정 (2026-10-03)

## 배경
같은 사용자가 매수 버튼을 연타하거나 탭 두 개로 동시에 요청하면, 현금 잔액이 음수가 되거나 보유 수량이 어긋날 수 있음. 현금은 `Member`에 있음 (013).

## 결정
매수·매도 때 `Member` 행을 비관적 락(`SELECT ... FOR UPDATE`)으로 잡고 처리한다. 집 사기도 `Member`의 현금을 차감하므로 같은 락을 쓴다. 락 순서는 항상 `Member`가 먼저다. 보유 종목 행은 회원+종목 유니크 제약으로 중복 생성을 막는다.

## 이유
- 환경이 EC2 1대 + RDS 1개라 DB 락만으로 정합성을 지킬 수 있음
- 락이 필요한 요청은 사용자 본인의 매수·매도·집 사기뿐이라 대기가 길어질 일이 적음
- 줄 세워서 하나씩 처리하므로 재시도·충돌 응답 처리 없이 로직이 단순함
- 현금이 `Member` 행에 있어서 그 행 하나만 잠그면 잔액 검증과 차감이 같이 보호됨

## 포기한 대안
- 낙관적 락(`@Version`): 락을 안 잡아 충돌이 드문 경우 빠름 / 충돌 시 예외가 나서 재시도나 에러 응답 처리가 필요함
- Redis 분산 락: 서버가 여러 대여도 락을 공유할 수 있음 / Redis 운영이 새로 필요하고 024(새 기술 금지)와 충돌하며, 락 이후에도 DB 정합성은 따로 지켜야 함. 서버를 여러 대로 늘리면 그때 다시 검토

## 결과
같은 사용자의 요청은 순서대로 처리되어 대기가 생김 (감수). 락 순서가 어긋나면 데드락 위험이 있어 항상 `Member`부터 잠가야 함. 평균 매입가 scale/RoundingMode는 019에 따라 구현 때 별도로 정함.
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 매수·매도·집 사기에 낙관적 락이나 Redis 락을 먼저 제안하지 않는다. 매수·매도 로직은 심장 ①이라 에이전트가 구현 코드를 쓰지 않는다. 관련: 013, 019, 024.
