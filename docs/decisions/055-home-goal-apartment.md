# 055. 홈 목표 아파트: 아직 못 사는 집 중 가장 싼 집

## 상태
확정 (2026-11-12)

## 배경
- 홈 목표 패널이 목업 고정값(태백 1,800만)이라 평가액이 늘어도 목표가 그대로였음
- 첫 집을 산 뒤에도 "첫 집 목표"로 남아 다음 행동이 보이지 않음
- 집을 사면 현금이 빠져 평가액이 내려가므로, 방금 산 집이 다시 목표로 잡힐 수 있음

## 결정
- 목표 = 최근 6개월·해제 아닌 거래 중 집값 > maxPrice인 가장 싼 거래 1건 (같은 값이면 id 작은 순). 내가 산 거래는 제외, 다른 회원이 산 거래는 포함
- maxPrice는 추천과 같은 `HousePriceRule.maxAffordablePrice(평가액)`. 응답은 추천과 같은 `AptRecommendResponse`
- `GET /api/apartments/goal`, 목표가 없으면(모든 집을 살 수 있음) 404 `GOAL_NOT_FOUND`
- 화면: 0채 "첫 집 목표", 1채 이상 "다음 집 목표". 진행 바 = 실시간 평가액 / 목표 집 계약금(40%). 다 모았거나 목표가 없으면 "계약금 모았어요!" + 부동산 링크
- 내가 산 거래 제외는 `not exists` 서브쿼리로 한 번에 조회

## 이유
- "못 사는 집 중 가장 싼 집"은 바로 다음에 닿을 수 있는 집이라 진행 바가 짧고 자주 차서 플레이 동기가 생김
- 추천과 같은 maxPrice를 쓰면 "추천 목록 맨 끝 바로 다음 집"이 목표가 되어 두 화면 숫자가 어긋나지 않음
- 응답 DTO와 `toResponse`를 재사용해 새 계산 없이 계약금·대출액이 추천과 같은 규칙
- `not exists`는 산 거래 id 목록을 넘기는 `not in` 방식과 달리 0채일 때 빈 목록 처리가 필요 없고 쿼리 1번
- 목표 없음을 빈 200이 아닌 `ErrorCode` 404로 두면 다른 오류와 같은 `{code, message}` 형식

## 포기한 대안
- 고정 목표(목업): 단순 / 평가액과 무관해 진행이 안 보임
- 살 수 있는 집 중 가장 비싼 집: 이미 살 수 있어 목표 역할을 못 함
- 사용자가 직접 고른 목표: 동기 부여가 큼 / 저장 테이블·화면 추가로 MVP 밖
- 서버 진행률 계산: 진행 바가 WebSocket 평가액(5초)보다 늦게 갱신됨 → 진행률은 화면에서 계산

## 결과
- 목표 집은 조회 시점 평가액 기준. 평가액이 오르면 진행 바만 차고 목표는 다음 조회(집 사기 무효화, 화면 재진입) 때 바뀜
- 모든 집을 살 수 있으면 목표 패널은 "계약금 모았어요!" 상태로 남음
- 번복 조건: 사용자 목표 선택 기능 도입 시
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 목표 기준을 추천 기준(평가액)과 다르게 바꾸지 않는다.
