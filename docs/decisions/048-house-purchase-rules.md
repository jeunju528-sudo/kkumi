# 048. 집 사기: 같은 회원 같은 거래 1번, 살 때 거래 재검증, 변신 단계는 내 마을 API

## 상태
확정 (2026-11-06)

## 배경
집 사기 API(`POST /api/houses`)를 만들며 정해야 했던 것
- 016은 "같은 거래를 여러 사용자가 살 수 있음(공유)". 같은 사용자가 같은 거래를 여러 번 사는 경우는 정해지지 않았고, ui-spec §8에는 "이미 계약한 단지" 상태가 있음
- 계약서 화면을 띄운 뒤 결제까지 시간이 지나면 거래가 해제되거나 6개월 기간을 벗어날 수 있음
- 홈 변신 카드에 쓸 변신 단계·집 수를 `/api/members/me`에 넣으면 member → house 패키지 참조가 생김 (house → member는 이미 있음)

## 결정
- 같은 회원은 같은 거래를 한 번만 산다 (409 `ALREADY_OWNED_DEAL`). 다른 회원끼리는 016대로 공유
- 결제 때 거래를 다시 검증: 해제됐거나 계약일이 오늘 − 6개월 이전이면 400 `DEAL_NOT_AVAILABLE`. 없는 거래는 404 `DEAL_NOT_FOUND`
- 순서: 회원 비관적 락(025) → 거래 조회·검증 → 중복 확인 → 현금에서 집값 40% 차감(047 올림, 부족하면 `INSUFFICIENT_CASH`) → `House` 저장 → 집 수로 변신 단계
- 변신 단계·집 수는 `GET /api/houses`(`MyHousesResponse{houses, houseCount, tier}`)로 제공하고 `MemberResponse`에는 넣지 않음

## 이유
- 싼 집 한 채를 5번 사서 바로 갑부가 되는 꼼수 차단, ui-spec과 일치
- 중복 확인을 락 안에서 해서 "도장 찍기" 연타에도 한 채만 생김
- 화면 검증은 계약서 진입 때(`GET /api/apartments/{dealId}`)도 하지만 최종 검증은 결제하는 서버에서 (014·015)
- 패키지 순환 참조 방지. 홈은 내 마을 쿼리를 같이 쓰면 됨

## 포기한 대안
- 같은 거래 중복 구매 허용: 구현이 단순 / 변신 단계 꼼수, ui-spec과 다름. 포기
- DB 유니크 제약(member_id, deal_id): 동시성까지 DB가 보장 / `House`는 공유 구매(016) 때문에 UK 없음으로 설계됨, 회원 락으로 이미 직렬화되어 이득 작음. 포기
- `MemberResponse`에 tier·houseCount 추가: 홈 요청 1개 절약 / member ↔ house 순환 참조. 포기

## 결과
홈 변신 카드는 회원 쿼리와 내 마을 쿼리를 함께 사용 (감수).
이 결정을 번복하려면 먼저 개발자와 논의 필요. 에이전트는 집 구매에 재고·독점 개념을 넣지 않는다(016). 관련: 014, 015, 016, 025, 047.
